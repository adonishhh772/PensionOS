# Data Onboarding \& Resolution Factory

## Data Migration, Intelligent Validation, Exception Resolution \& Reconciliation

### Final Functional, Regulatory, Data, Security, Architecture \& Test Requirements v1.0

**Reviewed:** 11 August 2026  
**Target market:** UK occupational pension schemes — DB, DC, CARE, Hybrid; configurable public-service and future NI overlays  
**Frontend:** React  
**Backend:** Python  
**Development DB:** SQLite  
**Production direction:** PostgreSQL-compatible HA relational database + secure object/evidence storage  
**Architecture:** Modular, configuration-first, event-driven/Kafka-ready  
**Core principle:** **Configure, Don't Customise**  
**Product principle:** **Bad data creates an actionable exception, not a migration-wide stop.**  
**Human-effort principle:** **Tell the validator what is wrong, why it matters, what evidence is needed, and the safest way to fix it.**  
**Status:** Implementation master specification. Production activation requires pensions, client/trustee, legal/privacy/security and operational sign-off.

\---

# 0\. Executive conclusion

The submitted Data Onboarding \& Resolution Factory design has the correct product direction and should be retained:

* universal/multi-format intake;
* pension-aware profiling;
* canonical mapping;
* AI-assisted suggestions;
* non-binary data quality;
* purpose-based readiness;
* exception compression;
* configurable resolution playbooks;
* deterministic remediation;
* continuous reconciliation;
* a human Exception Workbench;
* integration with Smart Transition and Scheme Build Studio.

However, the draft must **not** be implemented unchanged.

Mandatory corrections:

1. Do not hard-code `95% / 80% / 60%` mapping-confidence bands as universal production policy.
2. High AI confidence alone must never auto-map a material pension field.
3. Do not hard-code trust thresholds such as `0.95 / 0.70 / 0.50` as universal truth.
4. Do not calculate trust merely by summing weights from agreeing sources. Source authority, effective date, known defects, provenance and intended purpose matter.
5. Do not hard-code field materiality globally. The same field may be critical for one journey and irrelevant to another.
6. Do not hard-code Data Health Score weights `25/25/20/15/10/5` as regulatory truth. TPR's six dimensions should be measured separately. An overall score may be a configurable operational indicator only.
7. Do not hard-code exception-priority thresholds such as `>£1m = CRITICAL` or `>1,000 members = HIGH`. Priority/materiality must be policy-driven.
8. `ACCEPTED` is not enough for unresolved bad data. Use explicit `RISK\_ACCEPTED` with named authority, rationale, scope, expiry/review and evidence.
9. Do not use `overall\_trust\_score` or `migration\_readiness` as the sole go/no-go criterion.
10. Purpose readiness must evaluate a requirement set, not only a percentage.
11. Do not model the entire canonical pension estate as one flat `Member` object. Canonical contracts map to bounded contexts.
12. Data Onboarding must not become a second permanent Golden Member database. Authoritative data belongs in the owning PensionOS domains after promotion.
13. Historical source evidence and migration decisions are immutable; current member data is versioned/correctable.
14. Raw source records, lineage, evidence and affected populations must not be copied into uncontrolled JSON columns.
15. Use secure object storage/reference models for raw extracts and documents.
16. Missing columns should not automatically reject a whole file. Distinguish ingestion-mandatory, purpose-mandatory, optional, derived and unknown fields.
17. Do not use a fixed `MAX\_FILE\_SIZE` domain constant. Use streaming/chunking and infrastructure/configuration limits.
18. Duplicate source files should be handled idempotently; do not treat every re-delivery as a hard failure where a configured correction/replay path is valid.
19. Add XLSX explicitly. This is a common real-world onboarding format.
20. Treat Bacs/payment files separately from payroll input; Bacs is not a generic payroll source format.
21. Malware-infected documents/files must be quarantined and never parsed further until cleared.
22. PDF/DOCX/scanned-document extraction is advisory. Original evidence remains authoritative.
23. AI must not infer missing entitlement data, GMP, salary/service history or benefit values as fact.
24. AI may suggest a value only where policy permits and must show provenance/evidence.
25. Auto-remediation is allowed only under an ACTIVE deterministic remediation rule that has been tested and approved.
26. Do not auto-correct DOB, service, salary, GMP, benefit entitlement or other material pension values based only on a "likely typo".
27. Normalising representation is different from changing underlying meaning; model those separately.
28. Exception clustering must not rely on a hard-coded `pattern.confidence > 0.80`.
29. Exception compression must retain underlying member-level traceability.
30. Resolution Playbooks must be typed/versioned workflow definitions rather than arbitrary executable JSON.
31. Target resolution times in playbooks are client/operational policies, not pension-law deadlines unless sourced.
32. Use a Source Authority Model. Multiple low-authority agreeing sources do not automatically override a higher-authority source.
33. Preserve `KNOWN`, `UNKNOWN`, `NOT\_PROVIDED`, `NOT\_APPLICABLE`, `CONFLICTING`, `DERIVED`, `CONFIRMED\_NULL`, `PENDING\_REVIEW` as distinct data states.
34. Never replace `UNKNOWN` with a default merely to improve completeness.
35. Derived data must identify derivation method/version and source evidence.
36. Identity resolution must not treat NINO as a guaranteed unique key.
37. Valid multiple memberships/sections must not be incorrectly deduplicated.
38. Purpose readiness must operate at member, membership, arrangement, section/cohort and payroll-population levels where appropriate.
39. Dashboard Find readiness and Dashboard Value readiness are distinct.
40. Data Quality findings use TPR's six dimensions separately: Accuracy, Completeness, Consistency, Timeliness, Uniqueness and Validity.
41. Data Onboarding DQ rules must integrate with the operational Data Quality Engine rather than creating an incompatible permanent DQ universe.
42. Scheme-rule validation must consume approved Scheme Build Studio configuration; it must not duplicate pension rule logic.
43. Calculation validation must use the Calculation/Calculation Assurance capability.
44. Payroll validation must use Payroll and Payments domains.
45. Reconciliation must support more than counts/totals: field, entity, benefit, calculation, payroll, contribution, case, document/hash and control-total reconciliation.
46. Reconciliation tolerance is policy/configuration and can be exact for critical controls.
47. Continuous reconciliation must operate source -> staging -> promoted domain state, not only source -> final target.
48. Corrections after an earlier reconciliation must create a new reconciliation version; do not overwrite prior evidence.
49. Data promotion must use owning-domain ports/commands/APIs, never direct SQL into Member/Payroll/etc tables.
50. Promotion must be idempotent and produce a Promotion Receipt.
51. Bulk human correction must be governed; one approval can resolve a pattern only when an approved deterministic rule applies to every affected record.
52. Exception severity colours are operational classifications, not regulatory/legal labels.
53. `RED` should block the smallest affected purpose/scope. It should not automatically halt the whole scheme.
54. `BLACK` means potential transition-wide integrity/control concern requiring governance review, not automatic global shutdown.
55. Material/systemic findings should publish factual events to Governance/Breach; this module must not decide TPR/ICO reportability.
56. AI readiness is not a simple trust percentage. It depends on provenance, DQ, permissions, conflict state and retrieval policy.
57. Do not expose full member records/PII through Kafka/events.
58. Use transactional outbox/inbox; Kafka can become transport later.
59. Audit should be append-only/tamper-evident and reference evidence rather than duplicate sensitive payloads.
60. Raw onboarding extracts require restricted access, encryption, retention and secure deletion controls.
61. Normal automated tests must use synthetic/anonymised data, not live member PII.
62. Unit, integration, contract, architecture, security, reconciliation and regression tests are mandatory and are part of the implementation, not a later phase.
63. Claude Code must build the capability in bounded slices/PRs and stop after each slice.
64. **Configure, Don't Customise** applies to mapping packs, validation rules, source authority, materiality, playbooks, remediation, readiness and reconciliation.

# 3\. Core operating principles

1. **Bad data creates an actionable exception, not a migration-wide stop.**
2. **Progress what is safe.**
3. **Block the smallest affected scope.**
4. **Explain every defect in pension language.**
5. **Show the validator what to do next.**
6. **Compress repeated errors into root-cause decisions.**
7. **No silent defaults.**
8. **No AI-only correction of material pension data.**
9. **Approved deterministic rules execute bulk remediation.**
10. **Every value keeps provenance.**
11. **Every correction is reproducible.**
12. **Continuous reconciliation, not end-of-project reconciliation.**
13. **Authoritative domains own final data.**
14. **File format disappears after intake normalisation.**
15. **New source systems require adapters/mapping packs, not core pension code changes.**

# 113\. Absolute instruction to Claude Code

> This master specification is the architecture and testing source of truth. Do not build the whole Data Onboarding \& Resolution Factory in one pass.

> Implement only the assigned PR slice and stop.

> Bad data creates an actionable exception, not a migration-wide stop.

> Tell the validator what is wrong, why it matters, what evidence is missing, and the safest next action.

> Never convert UNKNOWN into a default value merely to make a record look complete.

> Do not use AI confidence alone to map or correct material pension data.

> Use Source Authority, provenance, effective date, DQ and purpose when assessing trust.

> Model TPR's six DQ dimensions separately; an overall health score is only an operational indicator.

> Keep all confidence, severity, priority, materiality, readiness and tolerance thresholds configurable.

> Use typed/versioned Mapping Packs, Resolution Playbooks and Remediation Rules.

> Never allow arbitrary executable Python/eval/exec in configuration/playbooks.

> Only ACTIVE, tested, approved deterministic remediation rules may auto-remediate.

> Preserve before/after evidence and make every correction reproducible.

> Block the smallest affected purpose/member/cohort; do not halt the entire onboarding unnecessarily.

> Use Scheme Build Studio for scheme rules, Calculation for calculations, Payroll/Payments for financial execution and Data Quality for ongoing DQ.

> Promote data through bounded-context ports/commands. Never write directly to another domain database.

> Reconcile continuously and preserve every reconciliation version.

> NINO alone is not a guaranteed unique identity key.

> Use transactional outbox/inbox so Kafka can be introduced later without domain rewrite.

> Never put full member records or unnecessary PII on event transport.

> Write unit, integration, contract, architecture, security and regression tests as part of every slice.

> A slice is not done because code compiles or the UI renders. It is done only when its required tests pass and the Code Success Report is produced.

> \*\*Configure, Don't Customise. Explain, Resolve, Reconcile.\*\*
